# Ongaku Renshuu (音楽練習)

A free, offline-first practice player for guitar and bass tab and piano parts. It runs as a static web page served from 127.0.0.1 by a tiny Python server. There is no build step, no bundler, and no package.json: edit the files and reload the browser.

## Layout

- `index.html` holds the whole app: CSS, markup, and one `'use strict'` IIFE. Sections start with `/* ---------- Name ---------- */` comments, in this order: Tunings, Demo songs, State, Parser (ASCII tab), Note text (piano), Audio (pluck synth), Transport, Rendering (tab view), Loop, Songs (load, edit, save, tracks), UI wiring, Guitar Pro import (also MusicXML through alphaTab, and the MIDI reader), Image import, SoundFont player, Instrument sound settings, YouTube play-along, Sheet music (VexFlow), Tab or sheet music view, Piano keyboard, ABC notation, Video imports (server API, piano-from-video), Karaoke, Voice practice, Start. Keep new code in the matching section, and add new sections just before Start.
- `ongaku-renshuu.sh` is the launcher (`ongaku` command): background `tools/server.py` on port 8765 (plain `python3 -m http.server` if tools/ is missing), `--karaoke URL [--original LINK] [--method bars]` / `--piano URL` import videos from the command line, `--setup-vocals` installs the vocal separator, writes `soundfonts/index.json`, `--get-soundfont` downloads GeneralUser GS.
- `install.sh` and `update.sh` install to `~/.local/share/ongaku-renshuu`, link `ongaku` and `ongaku-update` into `~/.local/bin`, and add a desktop entry. `update.sh` keeps the last 3 backups and supports `--rollback`.
- `vendor/`: unmodified third-party builds (alphaTab for Guitar Pro files, VexFlow with Bravura for notation). Loaded lazily with a script tag and a jsDelivr fallback. Never edit these; to upgrade, replace the file, keep its license next to it, and update `THIRD_PARTY_NOTICES.md`.
- `soundfonts/`: only `sonivox.sf2` is tracked. Downloaded or user fonts and `index.json` are git-ignored.
- `tools/server.py`: the launcher's web server (replaces `python3 -m http.server`). Serves the app, serves the media folder at `/media/` with byte ranges, and runs imports one at a time at low priority. API: `GET api/info` (includes `separator`, whether the vocal separator is installed, and `version`, the installed `VERSION`; the header shows the page's version and offers a reload when they differ), `GET api/library`, `GET api/jobs`, `POST api/import {kind:'karaoke'|'piano', url, method?:'auto'|'vocals'|'bars', original?}`, `DELETE api/media/<kind>/<id>`. After a karaoke import succeeds it queues a follow-up `lyrics` job (`FOLLOW`: `karaoke.py URL --lyrics-text`), behind any imports still waiting, when Ollama is up. Write calls need the `X-Ongaku: 1` header and a 127.0.0.1/localhost Host.
- `tools/karaoke.py` import flow (vocal method, from a link): read the link's title first (`quick_title`, YouTube's oEmbed page, a fraction of a second; `video_meta` runs beside it); if it is not a karaoke video (`KARAOKE_TITLE`) and no `--original` was given, it is the original song, so `find_karaoke_video` searches for the karaoke version and the link becomes `--original` (the song keeps the pasted link's id). The karaoke audio starts downloading and `vocalguide.build` starts its search at once (the audio, the video and the song length are callables; the length comes from whichever of `video_meta` and the audio arrives first). The video waits for the search (`searched` event, since a busy line makes the search's small requests crawl), then downloads picture only (`bv*[vcodec^=avc1]`) and `add_sound` muxes in the karaoke audio already downloaded (copied when AAC, converted when an Opus fallback), so the sound is fetched once and matches the file the guide was timed against. Lyric lines are read from the video while it downloads (`LinesProcess` with `avail`, the seconds downloaded so far from yt-dlp's progress: each piece is read from `video.mp4.part` once its part is in, again if it came up short; a few workers only, so the pitch tracking keeps the memory bus). The import ends once the guide and the lyric timing are saved (lines keep `box` and a 64-value `sig` until read). `--lyrics-text` then reads the text with Ollama, one call per distinct line (lines grouped by width and their unwiped `sig`), and unloads the model (`keep_alive: 0`) so the next import's separator gets the GPU. Lines are tracked against their latest look, so the colour wipe no longer splits one line into several. `say()` writes each JSON line in one call under a lock, since steps run in parallel.
- `tools/karaoke.py` and `tools/pianovideo.py`: video importers (numpy, ffmpeg, yt-dlp; Ollama optional for lyric text). They print JSON progress lines and write `MEDIA/<kind>/<id>/song.json` plus `video.mp4` and `source.json` (title and channel, so a rebuild can search again). MEDIA is `${ONGAKU_MEDIA:-~/.local/share/ongaku-renshuu-media}`; its `venv/` holds an up-to-date yt-dlp, installed automatically when YouTube blocks the system one.
- Karaoke pitch guides come from `tools/vocalguide.py` first (`--method auto`, the default): search YouTube for the original recording (`find_candidates`: ranked by length, with a gentler penalty for longer uploads such as music videos with a story intro, a bonus for verified artist channels, live performances and collaboration cuts pushed down, fan edits, covers, acapellas and multi-language compilations skipped; a recording counts as the song when its chroma gain is at least 0.12, or at least 0.06 with the beats lining up over 60% of the song (`matches`: songs on one chord loop, such as a lot of rap, never reach 0.12 even against the right recording; wrong songs in that gain band lined up on at most a third); `build` compares the first three and keeps the best `gain`), match it to the karaoke audio with bias-free chroma (`global_match` for the overall offset and key, then `offset_map`: chroma offsets in short windows near that offset, stray windows voted out, ends held), then sharpen the timing to about 10 ms from the beats (`refine_onsets`: onset envelopes matched within 0.15 s, scores pooled over 15 s so a pattern repeating every eighth note cannot pull one window off), separate the vocal with `tools/separate.py` (Demucs htdemucs, run in `MEDIA/vocal-venv`, which holds PyTorch and is installed on first use or by `ongaku --setup-vocals`; `vocalguide.Separator` starts it with `--serve` when the build begins, so the model is on the GPU before the song arrives; on the GPU eight 7.8 s pieces go through at once in half precision, about 3 s a song, stepping down to fewer pieces and then the CPU when memory runs out; the vocal is within -60 dB of the one-piece result and scores the same on the benchmark). `build` downloads the top-ranked original whole and separates it straight away, while the next two download as small low-bitrate copies (`download_audio(low=True)`) that are only compared; when one of those wins, it is fetched whole and aligned again, since an Opus copy can sit about 40 ms off. The karaoke track's chroma and onsets are computed once (`align(kf=...)`), follow the pitch with numpy YIN (`sung_line`: frames more than `BASS_GAP` semitones under the 2 s median of the line are tracked again with a per-frame pitch floor, since that is the bass leaking into the stem), keep only frames where the vocal stem is a real part of the original mix (`vocal_pitch`: vocal-to-mix ratio above -26 dB, aperiodicity under 0.45; dropouts up to 0.25 s bridged when the pitch carries on, and any gap up to 0.15 s (a consonant) filled with each side holding its pitch; octave slips folded; 50 ms median smoothing), split it into notes with hysteresis so vibrato does not chop held notes (`to_notes`: a change must hold 40 ms; fragments under 30 ms absorbed; each note judged by its sung part, so a quiet tail is trimmed and notes quieter than -24 dB against the mix dropped; each note's pitch is the median of its middle; the line between two touching notes moved, by up to 0.1 s, to where the voice crosses; lone notes under 0.12 s dropped; notes an octave off their neighbours moved back), then shift everything 10 ms later (`LATE`, measured). These settings were tuned against acapella uploads of 14 songs and checked on 10 more (24 songs: guide on vocal silence about 1.5%, clearly sung parts missed about 3%, within a semitone about 97%; the acapella reference ignores its own tracker glitches and bass leaks and is lined up with the stem by waveform cross-correlation); the scripts are not in the repo, so re-measure before changing them, and note that a longer minimum note looks tidier but costs pitch accuracy (60 ms: about 93%, 100 ms: about 90%). `to_notes(dp=cost)` swaps the hysteresis for a dynamic-programming split (`dp_notes`, a cost in frames per new note); a cost of 4 gives tidier notes (median about 184 ms) at about 92% within a semitone, so it is not the default. Only when the beats can't be matched does it snap phrases to the karaoke video's lyric-wipe line starts instead (`wipe_activity`, which measures `WBANDS` = 18 horizontal bands and leaves out bands that change in 45% or more of frames, such as moving backgrounds and scrolling pitch bars; `snap_phrases`). `analysis.timing` says which: `beats` or `chroma`. Downloads and stems stay in `MEDIA/karaoke/<id>/work/`. When that fails, `karaoke.py` falls back to reading the video's pitch bars (`--method bars` skips the vocal method; `--original URL` names the recording).
- `tools/omr.py`: sheet music from images with Audiveris (optical music recognition). `--setup` downloads the Audiveris Ubuntu .deb (it carries its own Java) and unpacks it into `MEDIA/audiveris` with no root. A page is read at three sizes (`SCALES`) in parallel with relaxed staff-length limits (`CONSTANTS`, so a short last line is kept); each reading is repaired (`repair`: a time signature inferred when none was read; a voice short of its bar gets back the rest, or the dot of the note before, that its notes' x positions say is missing; bars that make no sense are left alone), then `vote` keeps, bar by bar, the version most readings agree on, and `join_pages` appends later pages. The server's `POST api/omr {images:[base64]}` saves the pages in `MEDIA/omr/<n>/` and queues an `omr` job; `POST api/omr-setup` queues the install; `api/info` says `omr` when it is installed. The app's Import from image uses it for sheet music by default (`settings.sheetReader`, `effReader()`), loading `score.musicxml` through the MusicXML importer. Measured on 11 pieces engraved by Verovio in three music fonts: 97 to 99% of notes exact (a local 7B vision model read about 11%); what is left is mostly whole notes in the Leland font and unusual pickup bars.
- `karaoke-demos/`: the bundled karaoke demos (public domain songs), built by `tools/make_demo_karaoke.py` with FluidSynth: `<id>/song.json` (`audio_only: true`), `<id>/audio.m4a`, and `index.json`, which the app reads directly so demos work without the server. To change a demo, edit the song table in that script and run it again.
- Voice practice exercises (`VP_EX`, `vpPlan`): the common warm-ups (five-note scale, falling five, triad, arpeggio, staccato arpeggio, octave and scale down, major and nine-note scales, intervals, octave slide, siren), each pattern labelled with movable-do syllables (`solf`), climbing a semitone a round as far as the voice range allows.
- `tools/check.sh`: syntax checks. Run it after every change.

## Data model

- A song: `{id, title, artist, bpm, cpb, kind, fmt?, tuning, tab, tracks?, track?, video?}`. `kind` is `'tab'` (ASCII tab in `tab`, `tuning` is a preset key or an array of MIDI numbers, highest string first) or `'notes'` (piano or melody, `tuning` null). For `'notes'`, `fmt: 'abc'` means `tab` holds ABC notation (the default for new piano songs); without `fmt` it holds the older simple note text. ABC is read by `abcToNoteText()` and then `parseNotes()`, and `noteTextToAbc()` writes it. `cpb` is grid columns per beat; for note songs it is derived from the text on parse.
- Multi-track songs keep every track in `tracks[]` (`{name, kind, fmt?, cpb, tuning, tab}`); the top-level fields mirror the current track, and `syncTrack()` writes edits back.
- `parsed = {kind, steps[], measures[{start,len}], warnings[]}`. A step is one grid slot. Tab notes are `{s, fret, dead?, legato?}`; note-text notes are `{midi, dur, voice, staff}`. `noteMidi(n)` turns either into a pitch.
- Timing: `stepDur()` is seconds per step at the current speed. The Web Audio scheduler (`tick`) runs ahead of `ctx.currentTime`; the cursor is drawn from the scheduled `timeline`. In video mode the YouTube player is the clock instead (`videoTick`, `vtNow`).
- Both views (tab and VexFlow notation) fill the same arrays: `rowEls`, `rowsMeta`, `stepX`, `stepNext`, `stepRow`, `rowGeo`, `noteGroups` (elements with `data-k`), `bandEls`, `mnEls`. `setCursor`, looping, and click-to-seek only rely on these, so a new view must fill them too.
- `video` (`{id, offset}`) belongs to each song and is written to the library as soon as it changes (`persistVideo`); demos keep theirs, with the fitted tempo, in `ongaku.videos` keyed by demo id.
- Karaoke songs live on disk, not in browser storage: `{id, title, artist, duration, video, notes:[[start, dur, midi]], lyrics:[{t0, t1, s0, s1, wipe:[[t, fraction]], y, text}], analysis, key_confidence, guide?, contour?}`. `guide` is `'vocals'` or `'bars'` (older songs have neither and came from bars). Vocal guides keep the singer's real octave and add `contour:[[start, step, [midi, ...]], ...]` (runs every 50 ms) for the thin exact-pitch line; their `analysis` names the original recording and the match quality. Piano video songs: `{title, artist, youtube, bpm, start, notes:[[start, dur, midi, 'R'|'L']]}`, turned into an ABC song by `pianoVideoSong()`.
- The karaoke lane draws `tidyNotes(notes)`: notes under 80 ms (`TIDY`) merged into the touching note nearest in pitch, each drawn note keeping its exact `parts`; a sung frame is judged against whichever is closer, the drawn bar or the exact part under it (`partAt`). Doing the merge in vocalguide.py instead costs about 5 points on the acapella benchmark (96.9% to 92.2% within a semitone), so the stored notes stay exact. The lane is always solid, since most karaoke videos have their own pitch bars under it, and its pitch range ignores notes under 0.12 s.
- The piano keyboard can show falling notes above it (`settings.falling`, the Falling notes button or F, shown only while the keyboard is). `computeSounding()` also fills `fallNotes` (`{k, e, midi, lh}` in steps, sorted by start), and `drawFall()` draws them each frame from `playX`, the continuous playhead `setCursor` keeps, 3 s ahead (`FALL_SEC`), repeating the loop when one is on. The sheet music or tab stays in view above.
- Export (Library, `#expFmt`/`#expGo`, section Export): `exportTracks()` turns every track into bars of events in 96 units per quarter, written by `toMusicXml` (tab tracks as a TAB staff with string and fret), `toMidi` (format 1; tab notes ring until their string is played again, unisons cut), `toGuitarPro` (the MusicXML read by alphaTab and written by its `Gp7Exporter`), or the current track's own text (ABC, or ASCII tab with a title, tuning and tempo header that the text importer reads back). All demos survive every round trip (export, import, compare notes).
- Tab notes may carry `slap: 'T'|'P'` (from `T5`/`P7` or a T/P line above the staff).
- Browser storage keys: `ongaku.library`, `ongaku.settings`, `ongaku.current`, `ongaku.videos`, `ongaku.karaokeQueue`, `ongaku.karaokeAdjust` (key shift per song), `ongaku.karaokeScores`. Settings also keep `karaMethod` (`'auto'` or `'bars'`), `karaLanePos` (`'top'` or `'bottom'`) and `karaLevel` (`'easy'`, `'normal'`, `'hard'`, `'pro'`; see `LEVELS` in the Karaoke section: pitch window, half-credit window, unjudged start of each note, whether the octave counts, share needed for full marks). Karaoke best scores are keyed by song id for Normal and `id@level` for the other levels. `karaExtra` (Score extras) counts singing with no guide note (more than 0.4 s from any note) as zero-credit time. Voice practice keeps `voiceType` (`'low'`, `'mid'`, `'high'`, `'custom'`), `voiceLow`/`voiceHigh` (from Find my range), `voiceSpeed`, `voiceEx`, and best scores in `ongaku.voiceScores`. Storage is per origin, so the port must stay 8765 or users lose their saved songs.

## Rules

- Keep it offline-first and dependency-free at runtime. Internet is optional (YouTube, Google Fonts, the jsDelivr fallbacks).
- Wrap every `localStorage` access in try/catch, and keep old saved songs loading after any data-model change (add fields with defaults; never rename existing ones without a migration).
- User-facing text is plain, friendly English, and never uses em dashes.
- Demo songs must be public domain or original.
- Version lives in two places that must match: `VERSION` and the `ongaku-renshuu-version` meta tag in `index.html`. Bump both for any user-visible change.
- Shell scripts use `set -euo pipefail`, must pass `bash -n`, and never need root except for explicit `sudo pacman` steps.

## Checking your work

    tools/check.sh                         # bash -n on the scripts, node --check on the inline JS, version match
    python3 -m http.server 8765 --bind 127.0.0.1    # then open http://127.0.0.1:8765/

If Playwright is available, test in a headless browser: load the page, open the Ode to Joy demos, press play, switch between Tab and Sheet music, and watch for page errors. Check both light and dark color schemes for UI changes.

## Releasing

Commit, then `git tag vX.Y.Z && git push origin vX.Y.Z`. The GitHub Actions workflow checks the version numbers, builds `ongaku-renshuu.zip`, and attaches it to a release.
